# تقرير الاعتماد الصارم لقسم الحسابات — Ensan Finance V2

**مصدر المتطلبات:** `الحسابات.docx` (537 سطراً مستخرجاً ومراجعاً كاملاً)
**النطاق:** الحسابات والخزائن والتبرعات والمصروفات والتوريدات والبنك والشيكات والعهد والتخصيصات.
**القرار:** لا يجوز اعتماد طبقة الحسابات القديمة كسجل مالي رسمي. نُفذت نواة مالية V2 مضافة وآمنة، ويجب ترحيل البيانات إليها وفق الخطة أدناه قبل التحول التشغيلي.

## هيئة المراجعة والمناظرة

| الشخصية | الاختصاص | الحكم |
|---|---|---|
| الأستاذ إلياس وارد | معماري بيانات مؤسسية | فصل النقد الفعلي عن الأموال المخصصة وإعادة بناء مصدر الحقيقة |
| د. نادية المصري | محاسبة صناديق ورقابة داخلية للمؤسسات غير الربحية | القيد المزدوج والموافقات والمطابقة لا بد أن تكون إلزامية وذرية |
| نادر الخصم | المهندس الناقد/اختبار عدائي | رفض أي حذف أو تعديل لاحق أو اعتماد ذاتي أو سباق أرصدة |
| فريق الإدارة المفترض | المدير المالي، مدير البرامج، أمين الصندوق، مدير التحصيل، المراجع الداخلي | لا يملك أي طرف تنفيذ دورة المال كاملة بمفرده |

## ما تقرره الوثيقة بصورة صحيحة

- الخزينة الإجمالية تقرير تجميعي وليست خزينة تستقبل حركة.
- المشروع والحملة والصندوق تخصيصات تحليلية، وليست نقداً إضافياً.
- التحويل بين خزانتين ليس إيراداً ولا مصروفاً.
- العهدة ذمة على الموظف، ولا تصبح مصروفاً إلا بفواتير معتمدة.
- الشيك لا يخصم البنك نهائياً قبل تأكيد الصرف أو المقاصة.
- الصرف الموجه يجب أن يخفض نقداً فعلياً وتخصيصاً/صندوقاً مناسباً في معاملة ذرية واحدة.

## التشخيص المثبت في النظام الحالي

| الخلل | الدليل البرمجي | الأثر |
|---|---|---|
| مصادر حقيقة متعددة | `treasuries.current_balance` و`treasury_transactions` وقيود يومية وتبرعات ومصروفات | يمكن أن تتعارض التقارير |
| حذف/تعديل حركات | `TreasuryController::updateTransaction/deleteTransaction` و`TreasuryService::deleteTransaction` | إعادة كتابة التاريخ المالي |
| القيد اختياري عند المصروف | `TreasuryIntegrationService::processExpenseFromTreasury` يلتقط فشل القيد ويكمل | نقد خارج بلا دفتر أستاذ |
| مشروع/حملة كخزينة | `Treasury::TYPE_PROJECT/TYPE_CAMPAIGN` | خطر العد المكرر للأموال |
| عدم وجود دورة توريد أو عهدة أو مطابقة | لا توجد كيانات وسطور وحالات مستقلة | لا يمكن إثبات التسليم والاستلام أو الرصيد البنكي |
| تخصيصات JSON | `donations.split_allocations` | لا سلامة مرجعية ولا منع تجاوز الرصيد المقيد |
| سباق الرصيد | فحص الرصيد قبل transaction بلا `lockForUpdate` | احتمال صرف زائد متزامن |

## ما نُفذ في هذا التغيير

1. هجرة **إضافية** `2026_11_19_180000_create_finance_v2_ledger_tables.php`؛ لا تحذف ولا تعدل تاريخ V1.
2. دفتر أستاذ V2: قيود متزنة، رقم فريد، مفتاح idempotency، فترة مفتوحة، وعكس مرتبط بالأصل.
3. دليل حسابات V2 منفصل وحسابات نقدية فعلية فقط، ومصفوفة صلاحيات مستقلة لكل حساب نقدي.
4. صناديق وتخصيصات مقيدة مع `fund_balances` مقفلة صفياً لتفادي سباق الصرف.
5. تحويل نقدي بحالة انتظار الاستلام؛ لا ينشئ القيد إلا عند تأكيد المستلم.
6. بنية للعهد، تسوياتها، المطابقة البنكية، أرقام المستندات، والموافقات المالية.

## بوابات لا تقبل التفاوض قبل الإنتاج المالي

1. تعطيل مسارات V1 التي تعدل/تحذف حركات المال للحسابات المرحّلة.
2. كل event مالي يمر فقط عبر `LedgerPostingService` داخل transaction واحدة.
3. ترحيل رصيد افتتاحي معتمد بعد جرد خزائن ومطابقة بنك وعهد وشيكات معلقة.
4. تشغيل مزدوج ومقارنة يومية: دفتر الأستاذ = أرصدة النقد = الصناديق = البنك بعد التسويات.
5. اختبار ضغط متزامن لتحويل/صرف واحد؛ لا تجاوز للنقد أو للصندوق.
6. منع اعتماد المنشئ لنفسه، وحدود اعتماد حسب المبلغ والنوع والصندوق.
7. إقفال فترة وإعادة فتح منفصلة بسبب واعتماد أعلى؛ لا تبديل مباشر للحالة.

## حدود التنفيذ الحالية بشفافية

تم تنفيذ النواة وقواعد الكتابة الآمنة ومخطط الكيانات، **لكن لم يُحوّل التاريخ القديم تلقائياً ولم تُبدّل شاشات V1 بعد**؛ تنفيذ التحويل بلا جرد وتسوية معتمدة سيكون أخطر من إبقاء البيانات للقراءة. هذا موثق كخطة قطع تشغيلية، وليس نقصاً مخفياً.

راجع التفاصيل في [هيكل النظام](01_SYSTEM_ARCHITECTURE.md)، [قاعدة البيانات](02_DATABASE_DESIGN.md)، و[خطة التشغيل والتحقق](03_IMPLEMENTATION_AND_CUTOVER.md).
